# devnull-claude-plugin

An unofficial Claude Code mod for /dev/null (https://dev-null.sh): post and reply from a Claude Code session, see your newest commits in a pane, and get told when someone replies. Public and open source at https://github.com/humunuk/devnull-claude-plugin. It is not made by or affiliated with dev-null.sh, and the README and the plugin description say so.

People install this into their own Claude Code sessions, where it runs `ssh-keygen` against their SSH agent and talks to the network for them. Every rule below exists to keep that safe. Where a rule and a convenience conflict, the rule wins. Where something is not covered here, stop and ask instead of choosing.

## Layout

The repository root is the mod and its own marketplace:

- `.claude-plugin/plugin.json` (`"name": "devnull"`) and `.claude-plugin/marketplace.json` (one entry, `"source": "./"`)
- `hooks/hooks.json` (`{ "modules": ["./register.tsx"] }`) and `hooks/register.tsx`, which only wires the feature modules
- One module per feature (`hooks/setup.ts`, `hooks/posting.ts`, `hooks/pane.tsx` with its load and timer in `hooks/pane-core.ts` to avoid import cycles, `hooks/alerts.tsx`), each exporting `registerX(on)`: it hooks `command.run` on `{ command: 'devnull' }`, takes its own subcommand and passes every other run on with `next(e)`. `hooks/commands.ts` is the innermost hook and answers whatever no feature took with the usage text, so `register.tsx` registers every feature before it (a plugin's hooks on one event nest in registration order, first outermost). A feature's logic gets closures over its `$` calls, so it is tested without the engine. On 2.1.304, `claude plugin validate` accepts `$` handed to a directly called, imported function, and refused it handed to a function picked at run time from a table. It also allows a single unmatched hook per event across the whole mod, so the mod's one `session.end` hook sits in `register.tsx` and calls what each feature exports to stop (`endPane`, `endAlerts`); a new hook on an event another module already hooks needs a matcher of its own or the same folding.
- Every test world loads the whole mod, so a feature's tests must keep the others quiet (the pane's test store answers `alertsOn` with `false`, so the alerts poller sends nothing there).
- `hooks/lib/`: pure helpers that never touch `$`
- `$.state` atoms live in a feature-level module outside `hooks/lib/`, together with the accessors that read and write them (the recent-commits list in `hooks/recent.ts`: `readRecent($)`, `storeRecent(...)`). Checked in review on 2.1.304: `claude plugin validate` accepts a state read or write only in the file that defines the atom as a const, refuses an exported reference const, and needs the `PluginState` entry written out inline (`devnull: { recent: ... }`); a named type alias there is refused once something reads it.
- `types/index.d.ts`: the `$.state` contract, named in `plugin.json` as `"types"`
- `tests/*.test.ts(x)`
- `tsconfig.json`: the engine's (it extends `.claude-plugin/types/tsconfig.json`) plus `"noEmit": true`, so a typecheck before the first load writes nothing; committed (the engine writes its own only when the file is missing)
- `package.json` and `package-lock.json`: development tooling only, TypeScript pinned to exactly 7.0.2. The mod has no runtime dependencies and never gains one.
- `.claude-plugin/types/` is written by the engine and git-ignored by it. Never edit or commit it.

## Commands

- `npm ci --ignore-scripts` installs the tooling.
- `npm run validate` runs `claude plugin validate .`
- `npm run typecheck` runs `tsc -p .` (it needs `.claude-plugin/types/`, which exists once Claude Code has loaded the mod from this folder; `tsconfig.json` sets `noEmit`, so a typecheck before that load fails without writing `.js` files).
- `npm test` runs `claude plugin test .`
- `claude --plugin-dir <this folder>` runs a session with the mod loaded; the folder is watched and the mod reloads on save.

## Scope

### Phase 1: now, on the allowed endpoints only

1. `/devnull setup`: pick the signing key from the SSH agent's Ed25519 keys and RSA keys of at least 2048 bits (shown by SHA-256 fingerprint) and enter the /dev/null username. After the key lookup, `GET /api/v1/users/<username>` must answer 200 with `data.username` equal to the typed name exactly (the API matches usernames case-sensitively: a name in another case is a 404); only then are both kept in `$.store`. After a commit, if the username in the returned link differs from the stored one, tell the person.
2. `/devnull commit <text>` and `/devnull reply <hash or link> <text>`: post, signed with the chosen key. `/devnull reply` completes hashes in the prompt box: a `prompt.autocomplete` hook answers from the session's recent commits (`hooks/lib/recent.ts`), never from the network, and a row writes nothing but a validated hash; its description is cleaned text and the age. The same hook completes the subcommand names.
3. `/devnull`, registered with `immediate: true`: toggles the pane, and opens it with the keyboard focus in it (Siim, 2026-10-20), so `r`, `1` and `2` work at once and `Esc` returns to the prompt; the header shows a dim `esc to return` hint beside `r refresh`, only while the pane has the keys (`isFocused`), since Esc in the prompt would interrupt a turn. Opening it, once the engine has placed it, counts as seeing the new replies: the reply count in the status line clears, while the pane keeps each such commit's `+N new` mark and `open ↗` link until it closes. Replies to the person's own replies are alerted too, but the Mine list holds only top-level commits, so Mine starts with a short `New replies` section (Siim, 2026-10-20): one row per reply of theirs with new answers, its hash, `+N new` and an `open ↗` link, drawn while it is marked or alerted. Opening it always fetches a fresh list of the person's newest commits (public API, 20 per page) and draws only that page; its "updated" age is the pane's own fetch, and `+N new` comes from the reply alerts through their accessor. On the terminal only (rule 1), the pane has an input to write a new commit; a successful post from it, or from `/devnull commit` and `reply`, reloads an open pane, and its outcome stays drawn until the next submit.
   - Look, in a `git log` style: a header `/dev/null · @<username>` with `r refresh · updated <age>` on the right; per commit, one line with the short hash in the `warning` theme colour, then the age, `★ <stars>` and `↳ <replies>` in `subtle`, `+N new` in `success` bold (a pending commit never appears: the public list holds only approved commits, `->approved()` in upstream `UserCommitController`); under it up to 3 cleaned body lines, `…` when cut, and an `open ↗` link; at the bottom a rule and the input (`commit ›`, Enter posts). Theme keys only, so light and dark themes both work; no borders inside the engine's frame. Non-ASCII characters are `\u` escapes in the source.
   - States, all fixed texts: not set up (`Run /devnull setup to choose your key and username.`), loading, empty (`No commits yet. Type below, or /devnull commit <text>.`), and error (`Couldn't load commits (HTTP <status>). Press r to retry.`).
   - Keys while the pane has focus (it opens focused; `ctrl+x tab` or a click focuses it again): `r` refreshes, `1` and `2` switch tabs, Tab moves to the input, the arrows scroll, `Esc` returns to the prompt, `ctrl+x x` closes. Every close, the person's own included, stops the pane's requests. Placement is the engine's: docked beside the transcript in fullscreen from 110 columns, else inline above the prompt.
   - A tab row under the header, `1 Mine  2 Following`, switched with the number keys while the pane has focus (Buttons with hotkeys). The Latest and Trending tabs stay hidden until phase 2 (`3 Latest  4 Trending` then join the row).
   - The Following tab is built from the public API alone (Siim, 2026-10-20), and only when the person opens or refreshes it; it is never polled.
     - `GET /api/v1/users/<username>/following` (first page, newest follow first), then `GET /api/v1/users/<followed>/commits` for at most the first 20 followed users, one request at a time. The commits are merged newest first, at most 30 drawn, each with its author's `@username` on its line and a link from `commitLink(author, id)`.
     - A commit counts only when its author is the user whose list it came from. A user list that fails is left out and counted (`2 of 20 people could not be loaded`). A 429 stops the round where it is, honours `Retry-After`, and draws what arrived with a fixed note.
     - At most one round a minute: `r` sooner than that gets a fixed `wait <n>s` text. Rounds go in `$.state`, so switching tabs or reopening within the minute draws the last round without fetching.
     - The Following commits' hashes join `/devnull reply`'s completion, kept apart from the person's own recent list.
     - States, as fixed texts: following nobody (`You follow nobody on /dev/null yet.`), and none of them has posted.
4. Reply alerts: poll the person's newest commits and replies (`?replies=1`) every 60 s by default, never more often than every 30 s. When a `replies_count` rises, show a toast (`↳ N new replies on <hash>`, the engine's default 4 s, once per rise) and a count in the status line under the prompt (`devnull ↳N`). There is no band above the prompt (Siim, 2026-10-20); the status line is text only and cannot be pressed, so opening the pane is what marks the replies seen (Scope 3). Seen and toasted counts are kept in `$.store`, so a restart does not alert again. Reply text needs sign-in (phase 2), so phase 1 shows counts only.
5. `/devnull off` and `/devnull on`: stop and resume polling and alerts; `off` also closes the pane and stops its redraw timer, `on` does not open it. Kept in `$.store`.

### Phase 2: blocked upstream

Sign-in as a device, reply text, mentions, the unread count from `GET /api/v1/me`, and the Latest and Trending logs (and the signed Following log, which then replaces the public-API Following tab). Phase 2 starts only once dev-null-sh/dev-null.sh PR #585 (device authorization grant, RFC 8628) is merged and the terminal sign-in is described in that repository's `KNOWLEDGE_BASE.md` ("Signed API and devices"). Since `e204ebf` removed the API sections from the README, the knowledge base is the only upstream document that describes the API, and it gives no wire format: the endpoints, requests and answers are read from the source, as the CLI rows below are (Siim, 2026-10-22). Check the PR's state on GitHub and the `production` branch each time; never go by an earlier answer. Build no part of it before then. Never use the `/mobile/authorize` flow with a `devnull://` redirect: that scheme belongs to the official mobile app.

### Not in scope

Images (the official script supports them, but `$.http.fetch` takes a string body, so a binary multipart upload is unverified), quotes, stars, follows, and any tool the model can call.

### Keyboard shortcut: not possible cleanly (checked on Claude Code 2.1.304)

A mod cannot register a key binding, and `~/.claude/keybindings.json` binds only built-in actions, none of which runs a plugin command. A `Button`'s `action` prop can borrow a built-in action's chord, but only while that button is on screen, and it would mean telling users to bind an unrelated engine action. Do not do that. The pane toggles with `/devnull`; it opens focused, `Esc` returns to the prompt, `ctrl+x tab` focuses it again, and inside it the built-in `ctrl+x x` closes it.

The base URL is the constant `https://dev-null.sh`. No setting, environment variable or response changes it.

## Signing a commit (verified with OpenSSH 8.9p1 on 2026-10-20)

- Payload: `<unix seconds>\n<nonce>\n<reply reference, or empty>\n<body>`, with no trailing newline. The nonce is 32 lowercase hex characters from `crypto.getRandomValues`, used once. The server accepts a timestamp within 300 s of its clock and spends each nonce (`app/Services/SignedCommits.php`, `app/Services/SshSignatures.php`).
- Body, as of upstream `230c004` (#805): after the server's `CommitBodies::normalize` (line endings to `\n`, runs of blank lines in prose collapsed) and `mb_trim`, it must be 1 to 40000 code points raw (`CommitBodyLength::MAX_RAW_LENGTH`), hold no prose link longer than 2048 characters (`Urls::MAX_LENGTH`), and count at most 4000 characters (`Commit::MAX_BODY_LENGTH`) with each prose link counted as at most 23 (`Urls::characterCount`); links inside code count at full length and are not checked for the 2048 limit (`withoutCode`). Before signing, the mod refuses only a body that is empty after trimming or over 40000 code points; the link-aware count and the link length are the server's to judge, since mirroring its URL parsing would drift. A 422 then gets one fixed text naming both limits (4000 characters with each link outside code counting as up to 23, and no link outside code over 2048 characters). Reply reference: a 7 to 12 character hex hash, or a `https://dev-null.sh/` commit link that holds the commit's UUID; validate it against those two forms before signing (`app/Queries/CommitByReferenceQuery.php`).
- Sign only through the SSH agent:
  1. `ssh-add -L` lists the agent's keys; keep the `ssh-ed25519` lines and the `ssh-rsa` lines of at least 2048 bits. Exit 1 means an empty agent only when stdout is exactly `The agent has no identities.`; with any other stdout it means the agent failed. Only the key whose fingerprint the person chose in setup is used. If the agent no longer holds it, stop and say so.
  2. Make a fresh directory with `mktemp -d` and write that one public key line to `<dir>/signing.pub`.
  3. Run `ssh-keygen -Y sign -n devnull-commit -f <dir>/signing.pub` with the payload on stdin; the signature comes back on stdout. No private key file exists next to `signing.pub`, so ssh-keygen can only use the agent: with the key missing from the agent it fails with "No such file or directory" and never prompts for a passphrase. Do not rely on `-U` for this: on OpenSSH 8.9 it still falls back to a private key file and asks for its passphrase.
  4. Remove `<dir>/signing.pub` by name, then `rmdir <dir>`. Never delete recursively.
  5. `X-SSH-Signature` is the signature's base64 lines (everything between the armour lines) joined without newlines. Refuse anything that is not `[A-Za-z0-9+/=]+`.
- The mod never reads `~/.ssh`, never handles a private key, and never sends any public key but the chosen one.
- The README states the requirements: Claude Code in a terminal (`$.process` is CLI only), OpenSSH 8.1 or later (`ssh-keygen -Y sign`), and an Ed25519 key, or an RSA key of at least 2048 bits, that is on the person's GitHub account and loaded in their SSH agent.

## Security rules

1. Only the person posts, from their own local session.
   - `/devnull setup`, `/devnull commit` and `/devnull reply` run only when `e.origin.kind === 'composer'`. Every other origin is refused, `bridge` (Remote Control) included.
   - The pane draws its input, and any other control that posts, only on the `terminal` surface, and the handler refuses a submit from any other surface. A surface is what a client declares (the types call it "a rendering fact and not a trust signal"), and no client attached over the wire can name `terminal` (Checked behaviour). On every other surface the pane shows the list without them.
   - The mod drops every prompt suggestion whose trimmed text starts with `/devnull` (`prompt.suggest`, answered `{ isShown: false }` without `next`), so a suggestion the model wrote is never a Tab and an Enter away from a post.
   - The mod registers no tool the model can call.
   - Accepted limits, written in the README: keystrokes another program sends to the terminal (`tmux send-keys`, computer-use tools) look like the person's typing, and still go through the person's tool permissions; other installed plugins are trusted code (Checked behaviour).
2. Nothing from dev-null.sh reaches the model. Other people's text (commit bodies, usernames, server error text) is drawn only in the pane, the status line and toasts; the prompt box's completion rows show other people's pattern-checked usernames and hashes but never their commit text (the types do not say whether a row's label or description reaches the model). A command's `text` and `context`, `prompt.compose`, `prompt.submit`, `session.append` and tool results carry only the mod's own fixed messages and the person's own text, including their saved username and their SSH agent's key fingerprints and cleaned key comments (`/devnull setup`), plus a commit id (a UUID) checked by its pattern and the server's HTTP status and Retry-After as numbers. A username from a server answer never goes there, even pattern-checked: on a mismatch the text says so without naming it.
3. All outside text is cleaned before it is drawn: strip C0 and C1 control characters except newline, ANSI and OSC escape sequences, and bidi controls (U+202A to U+202E, U+2066 to U+2069); cap the length; draw it as `Text`, never as `Markdown`.
4. Every link is built from validated parts by `commitLink` in `hooks/lib/links.ts`: `https://dev-null.sh/@<username>/commits/<uuid>`, the username matching `^[A-Za-z0-9-]{1,39}$` and the id a UUID. On the `terminal` surface the `@` stays raw; on every other surface it is written `%40`, because the engine draws a `Link` whose href holds a raw `@` as plain text there (Checked behaviour). A URL from a response is never passed on.
5. Every response is `unknown` until a hand-written guard accepts its exact shape. Anything else is an error shown to the person, never a guess. Success is only the exact expected answer: for a commit, a 201 whose body parses as `Committed: …`; for a key lookup, a 2xx whose first line is the key line sent. `$.http.fetch` follows redirects without telling, turns a redirected POST into a GET on 301 to 303, and drops `X-SSH-Signature` on a cross-origin redirect (Checked behaviour), so nothing else may be read as success.
6. `$.process.run` gets an argv array, a `timeoutMs`, and no outside text in any argument.
7. No secrets anywhere; phase 1 has none. `$.store` holds the chosen key's fingerprint and public line, the username, the seen counts and the on/off flag, and nothing else.
8. Poll politely: the interval floor above, back-off on errors, one request in flight per poller (the pane's lane and the alerts poller each keep one; a fetch that gets no answer takes 30 s to reject), one shared 429 hold for the whole mod (`paneNotBeforeMs` in `hooks/pane-core.ts`, read before every public-API request and set on every 429 with a usable Retry-After, by the pane, the Following round, the alerts and setup's profile check alike, since all of them hit one per-IP limit), every timer stopped when the mod is off or the session ends.

## Checked behaviour (Claude Code 2.1.304, 2026-10-20)

Checked with a throwaway probe mod run headless (`claude -p --plugin-dir <probe> "/probe ..."`), python3 servers on 127.0.0.x, a scratch Ed25519 key and a scratch `ssh-agent` on a relative socket, and the engine's types (`claude-code/index.d.ts` of 2.1.304; symbols named below). The fetch is Bun's (`User-Agent: Bun/1.4.4`).

- **`$.http.fetch` redirects, timeout, refused connection.** It follows 3xx by itself, to another host and to another port, and there is no option to turn that off: `HttpInit` has only `method`, `headers`, `body`, `auth` and `socketPath`, and `HttpResponse` has no final URL, so the mod cannot tell that a redirect happened. 307 and 308 keep the method and the body (a POST arrived as a POST with all 83 body bytes). 301, 302 and 303 turn a POST into a GET with no body. A custom header (`X-Probe`, so also `X-SSH-Signature`) is kept on a same-origin redirect and dropped when the origin changes (another host, or the same host on another port). `Content-Type` is kept either way. A server that accepts the connection and never answers makes the call reject after 30 s (30005 ms): `HooksError: <plugin>: $.http.fetch(<url>) aborted: no complete answer within 30000ms`. A refused connection rejects at once (3 ms) and gives no status: `HooksError: <plugin>: $.http.fetch(<url>) failed: ECONNREFUSED: ...`. Checked by a redirect server on 127.0.0.1 sending each code with a `Location` on 127.0.0.2 or another port, plus a server that reads and never replies and a closed port. Not checked: an https to http redirect, and how many redirects are followed. So the mod can never assume a request reached dev-null.sh as sent, or that `X-SSH-Signature` reached the host that answered: only the exact expected answer counts as success (rule 5).
- **A command's `text` reaches the model, for normal and `immediate: true` commands.** Run headless, `/probe tok <random token>` and `/probe-now <random token>` (registered `immediate: true`) each stored their text as a `<local-command-stdout>` row. The next request of a `claude -p --continue` run sent it as a user text block: the token is in that run's `api-request-blob` transcript entry. Asked to quote the output without running anything, the model gave the token back word for word, with the probe not loaded in that run. The types say the same: `text` is "the row the model also reads", and `context` is notes only the model reads (`CommandRunResult`, and reference.md on `CommandOutput`). An immediate command typed mid-turn was not seen running mid-turn, because a headless stream-json session queued it until the turn ended. `CommandSpec.immediate` says its `{ text }` "prints as an idle run's does". So rule 2 is needed as written.
- **`$.process.run` environment and the terminal.** The child inherits the whole session environment, `PATH`, `HOME` and `SSH_AUTH_SOCK` included (a dummy `SSH_AUTH_SOCK` and a marker variable given to `claude` both showed up in the child's `env`). `init.env` is merged over it, not a replacement: `HOME` was overridden, a new variable was added, and `PATH` and the rest stayed (`ProcessRunInit.env`: "Variables set over the host process's own environment"). The child can reach the person's terminal: its stdin and stdout are pipes, but it has the session's controlling terminal, in the foreground process group, and `exec 3<>/dev/tty` succeeded (run under `script` so `claude` had a pty). A prompting `ssh-keygen` could therefore read from the person's terminal, so the lone-`.pub` design is what prevents a prompt, not the sandbox. With that design, through `$.process.run` and with a pty present: with the key in the scratch agent, `ssh-keygen -Y sign -n devnull-commit -f <dir>/signing.pub` (payload on stdin) exits 0 in 16 ms with the armoured signature on stdout and `Signing data on standard input` on stderr. With the key missing from the agent, or with `SSH_AUTH_SOCK` naming no socket, it exits 255 in under 10 ms with no prompt and the same stderr in both cases: `Load key "<dir>/signing": No such file or directory`, ending in `\r\n`. Those two causes cannot be told apart from the output.
- **Byte equality of `stdin` and the fetch body: yes, both UTF-8, byte for byte.** Payload `1760000000\n<32 hex>\n\ntere õhtust 👋 test\n🎉\nlõpp` (78 UTF-8 bytes, no trailing newline). `sha256sum` run through `$.process.run` with it as `stdin` printed the same hash as Python's UTF-8 encoding of the text. The probe signed it through `$.process.run`, then POSTed it with `$.http.fetch` (`text/plain; charset=utf-8`, signature in `X-SSH-Signature`) to a local server that saved the raw body. The saved body was those 78 bytes exactly (`Content-Length: 78`), with no BOM and no added newline. `ssh-keygen -Y check-novalidate -n devnull-commit` on the saved body with the signature rebuilt from the header answered `Good "devnull-commit" signature`. The same check failed with one bit flipped at the same length, with a newline added, and on the body's UTF-16 encoding (the bit flip and the newline re-run in review).
- **Who can press the pane's `Button` or submit its `Input`: no plugin call and no model tool raises those events directly.** `ui.press`, `ui.input` and `ui.select` fire when a surface reports a press, an edit or Enter on an element a render hook drew (their docs under the events map). Nothing on `$` raises them: `EventCalls.ui` has only `render`, `resolve`, `scroll` and `focus`, and the `$.ui` noun has no press, input or select call. So no plugin can call them, and neither can the model, whose tools reach `$` only through a plugin's code. `$.ui.focus` and `$.ui.scroll` press nothing (`focus` acts only on the calling plugin's own sites; `scroll` also moves a transcript row while it answers the person's own input). A prompt from the bridge, a channel, a peer session or a scheduled trigger is a `prompt.submit` turn (`PromptOrigin`) and reaches the pane only through what the model then does. Surfaces report presses and edits too: a Remote Control client (`bridge`) is the person's own account, and a client attached over the session protocol (`session.attach`: the desktop app, an SDK host) sends them over the wire. Checked in review in the 2.1.304 binary: an incoming `ui_input` reaches only an element the engine drew for that client (otherwise it answers `{handled: false}`), a remote `ui_render` can name only `desktop`, `mobile` or `vscode` (never `terminal`), and an absent surface is taken as `desktop`; the types say a surface over the wire "is what the client declared, a rendering fact and not a trust signal: do not key policy on it". `mobile` has no `Input` today, which the types call a limit of its element table, not of the protocol. Rule 1 says which surfaces get the controls that post. The testing kit's `press` and `input` exist only under `claude plugin test`. Outside the engine, and not tested here: a tool that sends keystrokes to the terminal looks like the person's typing, for the pane and for a typed `/devnull commit` alike. Examples are the model's Bash running `tmux send-keys` when the session runs inside tmux, or the computer-use tools this build lists (`request_computer`). Such a call still goes through the person's tool permissions. Other installed plugins: the types confirm they share the chain and can see, rewrite or take over everything here. `UiInputArgument` says another plugin addresses a field by matcher and may rewrite `value` before our `onSubmit` sees it. A `ui.press` hook can answer `{ element }` and take the press. Any plugin can hook the pane's `ui.render`. `OpEventOf` makes every `$` call (`http.fetch`, `process.run`, `store.*`) hookable by any plugin above the caller, to rewrite, refuse or answer. So other plugins are trusted code and are outside this threat model.
- **A raw `@` in a `Link` href is drawn as plain text on every surface but the terminal.** The test kit says so for desktop, vscode and mobile ("its href holds a raw @"), and the 2.1.304 binary runs a strict href check for every surface that is not `terminal` (printable ASCII, https, no credentials, no raw `@`, canonical form). dev-null.sh serves `/%40<username>/commits/<id>` with 200 and no redirect (one read-only GET in review), so `commitLink` writes `%40` there and keeps the raw `@` on the terminal.

- **A link the model writes does not submit a prompt.** `PromptOrigin` stamps `composer` on "a click on a transcript link" as well as on Enter at the prompt, so Siim checked it by hand in his terminal (2026-10-20): a Markdown link the model wrote with the target `/devnull%20nope` was handed to the operating system as `file:///devnull%20nope` (the file manager answered that no such file exists), and the prompt stayed empty. Plain `/devnull ...` text in a reply is not a link. No design change.

## Working on it

- Tests mock `$.http` and `$.process` through `claude-code/testing` and cover the refusals as well as the happy path: wrong origin, malformed or hostile responses, 4xx, 429, timeouts, hostile text, a key missing from the agent. UI tests run on `terminal` and `desktop`.
- Experiments use a throwaway key and a scratch `ssh-agent` on a relative socket path. Never a contributor's own keys or agent, and never a real post to dev-null.sh from a test or an experiment.
- Comments explain why, for the next reader; nothing about how the code used to be.
- Source files are ASCII only; write any other character as a `\u` escape. File-writing tools have turned escaped bidi characters into real ones before, which hides code from a reader (Trojan Source). `grep -rnP '[^\x00-\x7F]' hooks tests types` prints nothing. Tool calls have also decoded a written `\uXXXX` escape into the literal character, breaking a regex: run that grep after every write, and write escape-heavy text through a script when a tool keeps decoding it.
